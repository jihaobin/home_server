# 服务人员发布服务审核与下架功能设计

日期：2026-05-13

## 背景

当前服务人员发布服务由两类线上数据组成：

- `service_personnel_skills`：服务人员可提供的服务项，包含服务描述、宣传图、服务次数等服务级信息。
- `service_personnel_pricing`：服务人员在某个服务项下配置的规格/定价，包含规格名、价格、币种、预计时长、启用状态等规格级信息。

用户端服务列表、搜索、人员详情通过这些线上表查询服务人员、服务项与规格。新需求要求服务人员每次新增或修改服务信息都经过管理员审核，并允许管理员在管理端下架已发布服务。为避免服务人员修改资料后立刻影响已上线内容，本期采用“待审核版本”模型。

## 目标

1. 服务人员每次新增或修改服务信息时，都只生成待审核版本，审核通过前不替换线上版本。
2. 管理员可以审核通过或拒绝待审核版本；拒绝必须填写原因。
3. 管理员可以在管理端下架已上线服务；下架必须填写原因。
4. 下架服务不再展示在用户端服务列表、搜索结果、服务人员详情可选服务中。
5. 审核通过、审核拒绝、管理员下架都给服务人员发送通知。
6. 服务人员端服务设置页展示待审核、拒绝原因、下架原因等状态。
7. 管理端使用三层表格：父表格为服务人员，第一层子表格为服务信息，第二层子表格为规格信息。

## 非目标

- 本期不做管理员“恢复上架”按钮。下架后服务人员可重新提交服务信息，审核通过后重新上线。
- 本期不改变平台基础服务目录 `services` / `service_categories` 的审核逻辑。
- 本期不把下架粒度做到单条规格。下架作用于“某个服务人员的某个服务项”，规格只作为服务项的子数据展示。
- 本期不重做通知中心，只复用现有 `NotificationPublisher`。

## 核心语义

### 待审核版本

服务人员保存服务信息时，后端创建服务发布审核稿，状态为 `pending`。审核稿保存完整快照：

- 服务人员 ID。
- 本次提交的服务列表。
- 每个服务的服务 ID、服务描述、宣传图文件 ID。
- 每个服务的规格列表，包括规格名、价格、币种、预计时长。
- 商户资质文件 ID、职业资质文件 ID。
- 提交时间、更新时间。

审核稿不会立即写入 `service_personnel_skills` / `service_personnel_pricing`。已有已通过线上版本保持可见；新增服务审核前不出现在用户端。

### 审核通过

管理员审核通过待审核稿后，后端在事务中把审核稿快照应用到线上表：

- 更新服务人员资质字段。
- 用审核稿中的服务列表同步 `service_personnel_skills`。
- 用审核稿中的规格列表同步 `service_personnel_pricing`。
- 把相关服务项标记为已上架、已审核通过。
- 审核稿状态改为 `approved`，记录审核人、审核时间。
- 发送审核通过通知给服务人员。

### 审核拒绝

管理员拒绝待审核稿时：

- 必须填写拒绝原因。
- 审核稿状态改为 `rejected`。
- 记录审核人、审核时间、拒绝原因。
- 不修改线上表。
- 发送审核拒绝通知给服务人员。
- 服务人员端服务设置页展示拒绝原因。

### 管理员下架

管理员下架某个服务人员的某个已上线服务项时：

- 必须填写下架原因。
- 该服务项进入 `taken_down` 状态。
- 记录下架管理员、下架时间、下架原因。
- 用户端列表、搜索、人员详情过滤掉该服务项及其规格。
- 发送下架通知给服务人员。
- 服务人员端服务设置页展示下架原因。

服务人员后续重新提交该服务项并审核通过后，可以重新上线。重新上线不需要单独恢复接口。

## 数据模型

### 新增审核稿表

建议新增 `service_personnel_offering_drafts`：

- `id`
- `personnel_user_id`
- `status`: `pending` / `approved` / `rejected`
- `submitted_snapshot`: JSON，保存完整提交快照
- `rejection_reason`
- `reviewed_by`
- `reviewed_at`
- `created_at`
- `updated_at`

约束：

- 同一服务人员同一时间只允许存在一个 `pending` 审核稿。
- 服务人员再次保存时，如果已有 `pending` 审核稿，则更新该草稿快照，而不是创建多条待审核记录。

### 新增服务发布状态表

建议新增 `service_personnel_offering_statuses`：

- `personnel_user_id`
- `service_id`
- `publication_status`: `active` / `taken_down`
- `review_status`: `approved`
- `take_down_reason`
- `taken_down_by`
- `taken_down_at`
- `last_approved_draft_id`
- `last_approved_at`
- `created_at`
- `updated_at`

主键：

- `(personnel_user_id, service_id)`

说明：

- 这张表保存服务项级别的审核后状态和下架原因。
- 规格级启用状态继续使用 `service_personnel_pricing.is_active`。
- 用户端查询必须同时满足：服务人员可用、平台服务可用、规格可用、服务项发布状态为 `active`。

## 后端接口

### 服务人员端

保留现有服务保存入口，但语义改为提交审核：

- `PUT /workSkill/service-offerings`
  - 入参沿用当前服务项和规格结构。
  - 后端校验服务 ID、规格、资质要求。
  - 写入或更新 `pending` 审核稿。
  - 返回审核稿状态和最近拒绝/下架原因摘要。
  - 不直接覆盖线上表。

服务设置页读取时需要返回：

- 当前线上已通过服务。
- 当前 `pending` 审核稿状态。
- 最近 `rejected` 审核稿原因。
- 已下架服务项及下架原因。

### 管理端

新增管理接口：

- `GET /admin/service-offerings`
  - 分页返回服务人员父表格数据。
  - 内含服务项数组，每个服务项内含规格数组。
  - 支持按审核状态、上下架状态、人员关键词筛选。

- `POST /admin/service-offering-drafts/:id/approve`
  - 审核通过待审核稿。
  - 在事务中应用快照到线上表。
  - 发送通过通知。

- `POST /admin/service-offering-drafts/:id/reject`
  - 审核拒绝待审核稿。
  - body: `{ reason: string }`
  - `reason` 必填，长度建议 1-500。
  - 发送拒绝通知。

- `POST /admin/service-offerings/:personnelId/:serviceId/take-down`
  - 下架已上线服务项。
  - body: `{ reason: string }`
  - `reason` 必填，长度建议 1-500。
  - 发送下架通知。

## 用户端过滤规则

所有用户端服务发现链路需要过滤下架服务：

- 服务人员列表。
- 服务搜索。
- 通过服务 ID 查找服务人员。
- 服务人员详情页中的可选服务与规格。
- 首页推荐或其他复用服务人员查询的入口。

查询条件必须排除：

- 没有审核通过状态的服务项。
- `publication_status = taken_down` 的服务项。
- `service_personnel_pricing.is_active = false` 的规格。
- `services.is_active = false` 的平台服务。

## 通知

复用现有 `NotificationPublisher`。

通知事件建议：

- `service_offering_review_approved`
- `service_offering_review_rejected`
- `service_offering_taken_down`

payload 字段：

- `userId`: 服务人员用户 ID。
- `personnelId`: 服务人员用户 ID。
- `serviceId`: 服务 ID，审核稿级通知可为空或包含受影响服务 ID 列表。
- `draftId`: 审核稿 ID。
- `action`: `approved` / `rejected` / `taken_down`
- `reason`: 拒绝或下架原因。
- `triggeredAt`

## 管理端页面

新增“服务发布管理”页面，遵循现有管理端页面结构和组件风格。

### 父表格：服务人员

字段：

- 服务人员姓名。
- 手机号或实名状态。
- 可用状态。
- 服务数量。
- 待审核数。
- 已下架数。
- 最近提交时间。

### 第一层子表格：服务信息

字段：

- 服务名称。
- 分类。
- 发布状态：已上架 / 已下架。
- 审核状态：待审核 / 已通过 / 已拒绝。
- 拒绝原因或下架原因。
- 最近更新时间。
- 操作按钮。

操作：

- 待审核服务：审核通过、审核拒绝。
- 已上架服务：下架。
- 已下架服务：不提供恢复按钮。

### 第二层子表格：规格信息

字段：

- 规格名称。
- 价格。
- 币种。
- 预计时长。
- 是否有效。

规格层只展示，不做下架操作。

### 原因弹窗

审核拒绝和下架都使用原因弹窗：

- Textarea 必填。
- 空白原因禁止提交。
- 成功后刷新当前表格并关闭弹窗。
- 失败时展示接口错误。

## 移动端服务人员页面

服务设置页需要展示：

- 保存按钮文案改为“提交审核”。
- 成功提示改为“已提交审核，等待管理员审核”。
- 存在待审核稿时展示“待审核”状态。
- 最近审核拒绝时展示拒绝原因。
- 服务项被管理员下架时展示下架原因。
- 下架服务重新编辑提交后，仍需等待管理员审核通过才重新展示给用户端。

## 测试策略

### 后端单元测试

覆盖：

- 服务人员保存服务信息只创建/更新待审核稿，不写线上表。
- 已有 `pending` 草稿时再次保存会更新草稿。
- 审核通过会在事务中应用快照到线上表。
- 审核拒绝缺少原因会失败。
- 下架缺少原因会失败。
- 下架后用户端查询不返回该服务项。
- 审核通过、拒绝、下架都会调用通知发布。

### 管理端测试

覆盖：

- 父表格展示服务人员。
- 展开后展示服务子表格。
- 再展开后展示规格子表格。
- 拒绝/下架弹窗原因必填。
- 操作成功后刷新列表。

### 移动端测试

覆盖：

- 保存成功后展示待审核状态。
- 拒绝原因展示。
- 下架原因展示。

## 验收标准

1. 服务人员新增服务后，管理员未审核前用户端不展示该服务。
2. 服务人员修改已上线服务后，管理员未审核前用户端仍展示旧版本。
3. 管理员审核通过后，用户端展示新版本。
4. 管理员拒绝后，线上旧版本不受影响，服务人员端展示拒绝原因并收到通知。
5. 管理员下架后，该服务不再出现在用户端服务列表、搜索和人员详情中。
6. 管理员下架必须填写原因，服务人员端展示下架原因并收到通知。
7. 管理端页面按“服务人员 -> 服务信息 -> 规格信息”三层表格展示。
8. 规格层不提供下架操作。
