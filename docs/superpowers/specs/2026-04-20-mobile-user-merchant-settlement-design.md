# 用户端按摩页商户入驻页面设计稿

> 目标：在用户端按摩首页新增“商户入驻”独立路由页面，按设计稿落地页面 UI、首页入口跳转，以及基于 `react-hook-form` 的本地表单校验能力；本期不接后端提交接口。

## 1. 背景与问题

当前用户端按摩首页 [massage-landing-screen.tsx](/mnt/f/home_server/apps/mobile-user/components/massage/massage-landing-screen.tsx) 已经包含“商户入驻”入口文案，但仍存在以下缺口：

- 首页入口没有点击行为
- 不存在对应的独立路由页面
- 设计稿 [pencil-new.pen](/mnt/f/home_server/pencil-new.pen) 中的招募页尚未在 Expo 用户端落地
- 页面缺少本地表单状态和输入校验，用户无法完成有效填写

同时，本次需求还有两个明确约束：

- 页面应作为独立路由存在，而不是在按摩首页内切换展示
- 表单校验必须使用 `react-hook-form`

本次设计的核心原则是：

- 复用现有 Expo Router 路由结构
- 新能力仅覆盖页面跳转与本地表单校验，不引入后端接口改造
- 以设计稿 [pencil-new.pen](/mnt/f/home_server/pencil-new.pen) 中的招募页画板为唯一视觉基准，代码实现必须优先向设计稿靠拢
- 在遵守设计稿的前提下，再兼顾 `apps/mobile-user` 当前的 NativeWind / Expo 页面约束
- 动态交互状态优先使用稳定实现，避免触发已知 `nativewind` CSS interop 问题

## 1.1 设计稿基准

本次不是“做一个商户入驻页”，而是“把给定设计稿转成 Expo 页面”。因此视觉实现基准明确如下：

- 唯一参考设计文件： [pencil-new.pen](/mnt/f/home_server/pencil-new.pen)
- 目标画板：`Merchant Recruitment Screen`
- 设计画板尺寸：`390 x 1349`

这意味着：

- 页面结构、色彩方向、卡片层级、标题排布、输入框风格、上传区样式、提交按钮形态都应先对齐设计稿
- 不允许在没有理由的情况下把页面实现成“通用表单页”或“团队习惯样式页”
- 允许的偏差只能来自 Expo / 现有资产限制，而不是因为文档没有写清楚

## 2. 设计结论

- 新增独立路由页面：`/massage/merchant-settlement`
- 在全局 Stack 中注册新页面，并提供中文标题
- 在按摩首页“商户入驻”入口补充跳转行为
- 新增页面组件 `merchant-settlement-screen.tsx` 承载页面 UI 和表单逻辑
- 表单状态与校验统一使用 `react-hook-form`
- 本期只实现本地校验与本地成功反馈，不接真实提交接口
- “上传本人生活照”区域本期只做静态占位，不做图片选择与必传校验
- 页面 UI 以设计稿中的黄色招募头图 + 米白表单主卡 + 橙色底部提交按钮三段结构为强约束
- 实现完成后必须对照设计稿进行视觉回归，而不是只验证“能显示、能提交”

## 3. 现状调研结论

### 3.1 已存在的能力

- `apps/mobile-user/package.json` 已包含 `react-hook-form`
- `app/_layout.tsx` 已统一管理用户端受保护页面的 Stack Screen
- `app/massage/index.tsx` 已作为按摩首页独立路由入口
- `massage-landing-screen.tsx` 中的入口条组件已经支持 `onPress`

### 3.2 当前限制

- 当前项目没有现成的商户入驻接口与上传接口，不适合本期直接接后端
- 按摩首页组件较大，新功能应避免把完整表单继续堆叠在首页文件中
- 用户端存在 NativeWind CSS interop 已知问题，动态切换单选态、错误态时应避免依赖风险较高的动态 className

### 3.3 必须避免的误区

- 不要把“商户入驻”继续做成首页内嵌区域
- 不要在首页文件中直接塞入整套表单实现
- 不要为了本地校验而引入新的表单库或自写分散状态
- 不要在没有接口契约的情况下伪造网络提交逻辑

## 4. 方案比较

### 方案 A：独立路由页 + 页面内 `react-hook-form`

做法：

- 新增单独路由文件
- 页面组件内部使用 `react-hook-form`
- 首页入口点击后跳转到该页面

优点：

- 与现有按摩首页解耦
- 路由语义清晰，符合 Expo Router 现有结构
- 改动范围可控，风险最低
- 后续接接口时，只需在页面内部替换提交逻辑

缺点：

- 若后续多个页面复用该表单，再抽组件会有一次轻量重构

结论：

- 本期采用

### 方案 B：独立路由页 + 单独抽离通用表单组件

优点：

- 结构更抽象，后续复用方便

缺点：

- 当前只有单页落地场景，抽象层会先于需求出现
- 初次实现成本更高

结论：

- 本期不采用，必要时后续再抽

### 方案 C：首页内切换展示招募表单

优点：

- 入口到内容切换更短

缺点：

- 不符合已确认的“独立路由页面”需求
- 会继续放大首页组件体积
- 返回导航与标题行为不自然

结论：

- 本期不采用

## 6. 页面结构设计

新增页面组件：

- `apps/mobile-user/components/massage/merchant-settlement-screen.tsx`

页面结构按设计稿拆分为以下几个区域：

### 6.1 页面根容器

- 根节点使用 `ScrollView`
- 设置 `contentInsetAdjustmentBehavior="automatic"`
- 底部留出安全区空间，保证小屏设备可滚动查看完整表单
- 页面外层背景应保持设计稿里的浅暖色，而不是默认白底

### 6.1.1 视觉层级总览

从设计稿看，页面视觉层级非常明确：

- 顶部是一个高辨识度的黄色横幅卡片，左侧大标题分两行，右侧是人物插画
- 横幅下方不是普通白底表单，而是一整块大圆角、带轻阴影的米白主卡
- 主卡内部先有“商户信息 / 请填写真实信息”标题行，再是连续的白色输入框
- “上传本人生活照”区域是带红色提示文案的独立块，不是普通输入框
- 页面底部是一个宽尺寸、橙黄色、高圆角的提交按钮

这部分层级必须在代码实现中直接体现，不能退化成通用列表布局。

### 6.2 顶部招募横幅

内容：

- 左侧主标题“商户招募启示录”
- 辅助标签/说明文案
- 右侧人物或插图视觉

实现策略：

- 优先直接按设计稿复刻黄色横幅的构图、分栏和文案层级
- 标题必须保持两行大字排布，不要压成单行
- 右侧应保留人物插画或高度近似的视觉占位，不能省略成人物缺失的纯文字卡片
- 若仓库没有完全一致的素材，允许使用近似资源，但必须保留“右侧人物插画 + 左侧标题”的构图关系
- 横幅整体应表现为单独的圆角卡片，而不是普通背景色块

### 6.3 表单卡片

内容：

- 卡片标题“商户信息”
- 右侧辅助文案“请填写真实信息”
- 多个输入项
- 上传占位区

样式策略：

- 卡片作为页面主体容器
- 使用大圆角、浅米白底色、轻阴影还原设计稿层次
- 卡片宽度应明显大于内部输入框，形成“外卡 + 内部白色字段”的层级
- 字段之间应保持设计稿中紧凑但清晰的纵向节奏

### 6.3.1 字段视觉要求

根据设计稿，字段视觉不是通用后台表单风格，而是偏移动端营销页表单：

- 输入框为白底、圆角、浅边框
- 每个字段左侧有固定标签，右侧为 placeholder 或交互控件
- 性别选择是行内单选，不是下拉或 SegmentedControl
- 单选选中态使用橙色强调色
- 上传区是白底小方块，内部只有加号，不要实现成普通按钮
- “图片不得超过8M”应作为红色提示文案保留在上传字段区域

### 6.4 提交按钮

- 位于页面内容底部
- 作为主 CTA，点击后触发表单提交
- 样式贴近设计稿的圆角橙色按钮
- 按钮宽度应接近主卡宽度，且明显大于普通字段按钮
- 不要使用默认 Button 组件外观直接替代设计稿按钮

## 7. 表单字段与校验设计

表单使用 `react-hook-form` 管理，字段如下：

```ts
type MerchantSettlementFormValues = {
    merchantName: string;
    gender: "male" | "female" | "";
    phone: string;
    age: string;
    intentCity: string;
    photoToken: string;
};
```

说明：

- `photoToken` 本期仅作为未来扩展占位字段，不参与必填校验
- `age` 本期按字符串处理，便于直接承接输入框值与本地正则校验

### 7.1 姓名

字段：

- `merchantName`

规则：

- 必填
- 提交时去除首尾空格后不能为空
- 长度建议限制在 2 到 20 个字符之间

错误提示建议：

- `请输入姓名`
- `姓名长度需为 2-20 个字符`

### 7.2 性别

字段：

- `gender`

规则：

- 必选
- 仅允许 `male` 或 `female`

错误提示建议：

- `请选择性别`

### 7.3 手机号

字段：

- `phone`

规则：

- 必填
- 去除空格后必须匹配大陆手机号格式
- 推荐使用 `^1[3-9]\\d{9}$`

错误提示建议：

- `请输入手机号`
- `请输入正确的手机号`

### 7.4 年龄

字段：

- `age`

规则：

- 必填
- 仅允许正整数
- 数值范围限制在 `18-65`

错误提示建议：

- `请输入年龄`
- `年龄需为 18-65 岁`

### 7.5 意向合作城市

字段：

- `intentCity`

规则：

- 必填
- 去除首尾空格后不能为空

错误提示建议：

- `请输入意向合作城市`

### 7.6 上传本人生活照

字段：

- `photoToken`

本期行为：

- 仅展示静态占位区域与加号按钮
- 不接图片选择
- 不做必填校验
- 可在组件内添加注释，说明后续可接入 `expo-image-picker`

## 8. 表单交互设计

### 8.1 表单库使用方式

使用：

- `useForm`
- 必要时对单选项使用 `Controller`

建议配置：

- `mode: "onBlur"` 或 `onSubmit`
- 首次提交前不强制显示全部错误
- 提交后显示对应字段错误

### 8.2 输入行为

- 手机号输入框使用数字键盘
- 年龄输入框使用数字键盘
- 文本输入框保留 placeholder，贴近设计稿语义

### 8.3 错误提示

- 错误文案展示在字段下方
- 颜色使用危险态/红色系
- 不做 toast 级别的逐字段报错，避免干扰输入过程

### 8.4 提交成功行为

本期提交通过后：

- 不发起网络请求
- 显示本地成功反馈

推荐行为：

- 使用 `sonner-native` 的 `toast.success("提交成功，稍后会有工作人员联系您")`

说明：

- 若团队希望避免引入额外文案，也可先使用 `console.log` + 成功 toast
- 成功后是否清空表单，本期默认不清空，以避免用户误触后无法回看

## 9. UI 实现约束

### 9.0 设计稿优先级

本页的 UI 决策优先级如下：

1. 设计稿视觉结构
2. 现有移动端组件与样式体系
3. 开发便利性

如果三者冲突，优先解释为什么无法对齐设计稿，而不是直接退回通用实现。

### 9.1 NativeWind 与动态状态

由于用户端已知存在 CSS interop 风险，以下交互态建议使用内联 `style` 控制动态部分：

- 性别单选选中态
- 错误边框态
- 提交按钮禁用态（如实现）

静态布局仍可继续使用 `className`。

### 9.2 滚动与安全区

- 页面第一层使用 `ScrollView`
- 底部额外留出 `insets.bottom` 相关间距
- 保证在键盘弹起或小屏设备上仍能完整查看表单

### 9.3 视觉贴合度

本期目标是“高相似度还原设计稿”，不是“做一个风格差不多的页面”。

允许的合理偏差包括：

- 顶部插画以现有资源或近似实现替代
- 阴影、渐变、装饰图做轻量化实现
- 上传区域先只做静态占位

不允许的偏差包括：

- 把顶部黄色招募横幅改成普通文字标题
- 把米白主卡改成纯白平面背景
- 把输入区改成与设计稿层级完全不同的通用表单样式
- 删除上传区域提示文案或改变其信息层级
- 把提交按钮退化成普通小按钮或默认主题按钮

## 11. 验证方案

实现完成后至少执行：

```bash
pnpm --filter mobile-user run type-check
pnpm --filter mobile-user run lint
```

验证重点：

- 新路由可以从按摩首页正常跳转进入
- Stack 标题与返回行为正确
- 必填字段与格式字段校验符合预期
- 提交成功时不会发请求，但会给出明确反馈
- 页面在常见手机尺寸下可以滚动完整展示
- 页面整体视觉层级与设计稿一致：黄色头图、米白主卡、白色字段、橙色提交按钮
- 标题排版、插画占位、字段分组、上传区提示文案不能明显偏离设计稿
- 若存在设计偏差，必须能指出是素材缺失、平台限制还是有意简化，不能是“文档没要求”

## 13. 风险与后续扩展

### 13.1 当前风险

- 若设计稿依赖特定插画资源，而仓库中没有现成素材，则需要近似实现
- 若后续很快接接口，可能需要把成功反馈替换为真实异步提交流程

### 13.2 可扩展方向

后续如需继续完善，可在当前设计基础上平滑扩展：

- 接入真实提交 API
- 接入 `expo-image-picker` 完成图片选择与上传
- 抽离通用表单项组件
- 为提交成功后增加结果页或返回引导
